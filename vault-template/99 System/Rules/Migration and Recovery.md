# Migration and recovery

The initializer is only for a new, empty destination. It will not modify an existing vault. Existing vault migration is an evidence-driven agent task, with the user approving the actual scope.

## Before changes

Confirm the root and access, inventory every file type, identify authoritative sources, and inspect current navigation and relevant settings without exposing secrets. Record note counts, source-record counts, attachment gaps, broken links, duplicate candidates, existing schemas, and intentionally historical material.

Make or confirm a separate recoverable backup before broad changes. Verify a sample restore into an isolated location. Sync alone is not backup. Do not rely on a vague statement that files are “in the cloud.” Keep recovery copies in the user's approved backup location, separate from the working vault.

## Plan

Produce the proposed personalized map and exact old-to-new paths. Identify equivalent Hubs to preserve, rules to reconcile, note formats to retain, imports requiring wrappers, collisions requiring decisions, and changes to Bases or pipelines. Identify what remains untouched.

Do not use the framework's default names as a reason to destroy stable existing entry points. A mature vault can retain its root Hub name and use a compact discovery pointer. Record approved deviations and update every affected instruction consistently.

Obtain approval for broad moves, merges, destructive handling, plugins, sync changes, and external actions where it is not already provided. This does not prevent completing authorized read-only planning or safe local preparation.

## Import in staging

Use the current official importer instructions for the chosen source. Preserve the original export and reconcile source counts and attachment availability. Do not promise that every app export preserves databases or metadata equally. Test a representative subset before committing to a full import.

Retain exact source fields, irregular names, timestamps, and missing values when they are evidence. Apply a clean maintained schema in wrappers and canonical notes rather than silently normalizing raw data. Keep missing records explicit.

Do not make staging the permanent organization by accident. Route current truth, active outcomes, future ideas, reusable knowledge, and inactive history separately after inspecting their real role.

## Migrate in bounded phases

Establish entry points and rules first. Resolve collisions before moves. Migrate a coherent subject group, repair links and views, validate, and keep a rollback map. Do not bulk-edit unrelated topics while a subject's identity is unresolved.

Use the operating contract for evidence and the routing guide for duplication and maintenance. Preserve a single original and a single canonical explanation. Keep source wrappers and data guides attached to their assets, with file extensions in links.

## Verify

Compare baseline and final counts with explanations for intentional differences. Check original file hashes where exact preservation matters. Parse YAML, resolve links and headings, walk Hub chains, inspect source links, verify capture identities, and exercise actual Base inclusion and exclusion.

Open the entry Hubs in Obsidian when available. A script can detect broken links; it cannot judge whether the human can navigate the result. Test the fresh-agent bootstrap and a sample retrieval task. Document unresolved attachment, data, authority, and integration gaps.

## Roll back safely

Stop new writes if a migration is corrupting data. Preserve the failed state for diagnosis under the user's access rules. Restore a tested backup into an isolated location, compare the intended state, and confirm that sync will not immediately reapply the defect. Do not change provider or sync settings without authorization.

Keep the path map, original-name map, snapshots, and relevant source hashes until the user accepts the migration. Fix an importer or generator that re-creates duplicates before claiming the recurrence is solved.

## Routine maintenance

Keep Inbox temporary, review real active outcomes, and record substantive decisions as they occur. Use the user's actual review cadence. Do not install a background organizer, schedule tasks, or invent recurring reminders merely because the guide mentions maintenance.
