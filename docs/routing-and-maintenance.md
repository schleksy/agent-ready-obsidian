# Routing and maintenance

## Preflight before structural writes

Confirm the exact root and effective permissions. For an existing vault, verify `.obsidian` or obtain confirmation that this is an intentionally uninitialized Markdown vault. Read the closest Hub, canonical candidates, and applicable rules.

Search filenames, current/former names, aliases, distinctive body phrases, backlinks, and capture IDs across the whole vault, including Archive. Compare candidate hashes, normalized bodies, metadata, dates, sources, and meaningful unique content. Choose `update`, `merge`, `split`, `create`, `move`, `archive`, or `leave unresolved`. Do not infer ownership or lifecycle from a nearby note.

## Ownership and lifecycle are separate

| Operational role | Default destination |
| --- | --- |
| Ongoing responsibility or current truth | `10 Areas/` |
| Finite committed effort with a finish condition | `20 Projects/` |
| Possibility that has not become a commitment | `30 Incubator/` |
| Reusable knowledge across efforts | `40 Resources/` |
| Inactive, completed, or superseded history | `90 Archive/` |
| Adopted vault-wide operating rules | `99 System/` |
| Correct home cannot yet be established | `00 Inbox/`, with the precise question |

An organization can have current operating context in Areas and a finite launch in Projects. Link the project to its owning Area. A person does not inherit the user's employer. A reusable method does not belong to whichever client happened to inspire it.

The seven roots are the installed default contract. Document an approved alternative rather than creating an eighth root casually. Never overwrite an established user's structure merely to match the starter.

## Create only necessary structure

A single durable note normally stays in its existing category. Create a dedicated folder and Hub for a subject with multiple durable notes, workstreams, attachments, or data. Search for an existing category Hub first. Do not create parallel categories with synonymous names.

Register the new subject in its parent. Every maintained note must have valid frontmatter and a `hub:` pointer. Do not create empty company, person, product, or project Hubs for appearance. Minimal root navigation in a new starter is the deliberate exception; it establishes the operating structure, not fictitious subject matter.

## Duplicate and collision handling

Suffixes such as `copy`, `copy 2`, or `1` are collision warnings, not proof of a new version. A legitimately numbered creative concept is not automatically a duplicate.

Choose the canonical note using verified current truth, stronger evidence, valid unique metadata, correct ownership/lifecycle, and existing meaningful links. Prefer the stable unsuffixed name only when the substantive factors are equal.

Before retiring a duplicate, preserve its unique valid content and source links in the canonical explanation. Repair links first. Do not permanently delete without specific authorization. Keep dated historical snapshots when they answer a distinct historical question. Never merge different people or projects just because names match.

## Mixed captures

Read the whole item. Split its distinct meanings for routing, not its preserved original bytes. A task, a future idea, a factual correction, and a source link may have different destinations. Route clear parts now; withhold only the uncertain part. Preserve one original source record linking every destination.

A request to change the vault, capture pipeline, templates, permissions, or agent architecture is a proposed system change. Read related captures together and establish intent before adopting it as policy. An agent's recommendation is not an adopted rule.

## Safe moves

1. Establish the complete old-to-new map.
2. Check every destination for collisions, case sensitivity, and external dependencies.
3. Preserve stable filenames unless the rename has a real reason.
4. Update full-path wikilinks, Markdown links, parent-Hub references, YAML relationships, source wrappers, and views.
5. Search for old names and paths after the move.
6. Validate the changed notes, incoming links, Hub ancestry, and intended views.
7. Keep rollback evidence and leave unrelated siblings alone.

A rename does not justify rewriting a source quote. Preserve the former name as an unambiguous alias when useful. Do not assign the current subject's alias to a rejected historical alternative.

## Maintenance is part of the change

A new paragraph is insufficient if earlier active metadata or instructions still contradict it. At the beginning and completion of work, inspect these dependencies and act on those that apply:

| Dependency | Required action |
| --- | --- |
| Canonical knowledge | Reconcile current status, body, outcome, next step, evidence, dates, decision scope, and reason |
| Discovery | Repair parent and relevant indexes, supported relationships, source routes, and meaningful backlinks |
| Templates | Update affected existing templates and instructions; remove unsupported assumed owners and states |
| Views | Verify the actual record appears and retired records are excluded; parsing YAML alone does not test a Base |
| Workflows | Fix the smallest authoritative rule behind a recurring failure instead of copying policy everywhere |
| Generators and imports | Correct in-scope causes when authorized; otherwise record the exact recurrence risk |
| Outputs and continuation | Preserve the useful artifact or durable source link, verification, remaining work, and decision reason |

This does not grant permission for unrelated broad refactoring, external configuration changes, or deletion. A missing decision blocks only dependent work.

## Dates, corrections, and supersession

Keep statement, effective, source, capture, edit, and verification dates separate. Use absolute dates and the original timezone where available. If a decision date is unknown, say so. `updated` means a note changed, not that every fact was freshly verified.

A fixed handoff does not establish that the whole engagement ended. Selecting a platform does not establish that its security controls are live. An old project is not automatically cancelled.

Mark precisely which decision changed, its successor, scope, evidence, and reason. Preserve unchanged decisions in the same note. Record stored corrections in the accuracy log; unresolved claims get `review-needed`, not an invented conclusion.

## Closeout checklist

- [ ] Ownership and lifecycle are supported.
- [ ] Canonical copies were searched and compared.
- [ ] No accidental suffix duplicate or parallel category exists.
- [ ] Active metadata, body, state, and next action agree.
- [ ] Governing Hub ancestry reaches the root without cycles.
- [ ] Parents, links, views, templates, and generators were checked where relevant.
- [ ] Originals and unique source information remain preserved.
- [ ] Changed links and headings resolve.
- [ ] Retired information is visibly historical.
- [ ] Corrections and open dependencies are recorded.
- [ ] No unrelated changes, invented facts, or unauthorized deletion occurred.
