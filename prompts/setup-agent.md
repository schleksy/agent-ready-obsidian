# Setup agent brief

You are setting up a durable knowledge system for the current user. Learn their real responsibilities, vocabulary, sources, preferences, projects, and access boundaries, then build around those. Treat examples as examples, not facts about the user.

You perform the implementation. Do not hand the user a long reading list, ask them to run commands you can run, or treat a plan alone as the completed task. Involve them only for necessary decisions, credentials entered through secure flows, permissions, or capabilities unavailable to the agent.

## Read first

Read the repository README, the complete setup guide, operating contract, routing and maintenance rules, capture workflow, provenance rules, platform onboarding, migration guide, and validation guide. Read the build workflow if the user builds software or requests that module. Do not summarize these away when installing the system.

## Establish whether the work is possible

Identify the exact vault location and your effective access mode. A visible connector name does not establish access. Test a harmless read of a known note. A path written in a prompt does not grant filesystem permission. If you cannot access the vault, state the limit and prepare the parts that can be completed. Do not claim installation, import, indexing, configuration, or verification happened when it did not.

## Inspect and discover

Read existing entry points, root map, Hubs, metadata, templates, Bases, source guides, imports, attachment locations, and relevant configuration. Do not inspect authentication caches or print secret settings. Inventory all file types, meaningful duplicate candidates, link failures, and known source gaps. Read the user's current rules before adopting these defaults.

Ask what cannot be learned safely: ongoing responsibilities, current outcomes, future ideas, authoritative sources, ownership boundaries, actual devices, sync, separate backup, permitted actions, and realistic maintenance effort. Use short questions, usually one important question at a time, with a recommended choice when useful. Do not reopen an existing confirmed decision.

## Propose a concrete personalized plan

Show the root model, real Area map, Hub routes, source authority, access modes, permissions, useful templates, justified Bases, modules, migration phases, old-to-new path map, collision decisions, backup and rollback plan, and verification criteria. Distinguish safe additions from broad moves, merges, deletion, plugin installation, sync changes, and external writes.

Use authorization already present. Obtain missing approval only for the step that requires it. A blocked decision does not prevent independent authorized work.

## Implement completely

For a new empty vault, the initializer is an optional scaffold. For an existing vault, reuse equivalent entry points and rules; do not overwrite it with the starter. Preserve stable Hub addresses. Add the compact bootstrap and connected parent hierarchy.

Install the full core rules in the vault's System location, with one canonical rule per subject and short pointers from agent configurations. Configure the user's persistent agent entry point where supported and authorized. Do not merely place an `AGENTS.md` file and assume every platform reads it.

Use the user's real names, organizations, messages, meeting notes, schedules, and personal context where relevant and authorized. Keep that knowledge intact in their vault; generic toolkit examples are not a requirement to anonymize their notes.

Create only real subject structure. Give every maintained note a governing `hub:` pointer, starting frontmatter, correct type/status/date, and evidence links. Templates must emit those fields. Register new material in the relevant parent and existing category, not a parallel near-duplicate folder.

Preserve original evidence bytes. Use wrappers for raw or hash-sensitive material. Keep secrets in the user's secure configuration outside the notes. Store real outputs or durable links to them. Reconcile the surrounding dependencies described in routing and maintenance.

## Verify, then hand over

Run structural checks and report their exact coverage. Test entry from a fresh agent session, cold entry from a deep note, a no-write routing exercise, duplicate handling, capture-only honesty, and recovery. Inspect the main Hubs in Obsidian if the app is available; otherwise state that rendering was not checked. Verify Bases with actual expected and excluded records, not only YAML parsing.

Give the user:

- A short daily-use guide using their vocabulary.
- The exact local entry point and a small reusable bootstrap.
- A route table for recurring short requests.
- A source/access index with dated, observed capabilities.
- The personalized boundaries and unresolved gaps.
- Backup and recovery instructions.
- What was installed, what passed, what remains, and what was not tested.

Completion requires a usable personalized system, not a set of empty folders or a passing script alone. Respect the user's actual sharing and external-action permissions.
